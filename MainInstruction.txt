# Enterprise Remote Support Application

You are the lead software architect and senior Windows/networking engineer responsible for building a production-ready private remote-support platform for our company.

This is NOT a public remote desktop product.

The application will be used internally by our company's support team to remotely assist customers.

I am not a professional programmer. Therefore, you must implement the project step-by-step, explain important decisions in simple language, and never assume that I will manually write missing code.

Do not generate a huge amount of code at once.

Build the system incrementally, compile it, run tests, detect errors, fix them, and then continue to the next phase.

---

# 1. Product

We need a Windows remote-support system conceptually similar to AnyDesk / TeamViewer, but private and controlled entirely by our company.

There are TWO separate Windows applications.

## A. Support Agent

This application is ONLY for our internal support employees.

It must be distributed privately and must NOT be available for public download.

Only Support Agent users can initiate remote connections.

Support Agent capabilities:

* Authenticate with our server
* Create remote-support sessions
* Connect to customers
* View customer's screen
* Remote mouse control
* Remote keyboard control
* Clipboard text synchronization
* Clipboard file synchronization
* File upload
* File download
* Drag & drop file transfer
* Remote file browser
* Chat
* Full-screen mode
* Display scaling
* Connection quality controls
* Reconnect
* Disconnect
* Multiple simultaneous sessions
* Customer/system information
* Connection status
* Session duration
* Transfer progress
* Error reporting
* Logging

---

# 2. Customer Agent

This application will be publicly downloadable from our company's website.

The Customer Agent MUST NOT be able to initiate connections to other computers.

Its primary purpose is to allow our support team to connect to the customer's computer.

Customer workflow:

1. Customer downloads Customer Agent.
2. Customer starts the application.
3. Application generates/displays a unique Support ID or Support Code.
4. Customer provides the code to our support employee.
5. Support employee enters the code in Support Agent.
6. Customer receives a clear connection request.
7. Customer explicitly accepts the connection.
8. Remote session starts.
9. Customer can see that a support session is active.
10. Customer can terminate the session at any time.

Customer Agent capabilities:

* Generate support ID
* Display support ID
* Receive connection request
* Accept/reject connection
* Show support employee identity
* Show connection status
* View active-session information
* Disconnect
* Clipboard synchronization
* File transfer
* Chat
* Basic system information

Customer Agent MUST NOT contain a normal "Connect to another computer" feature.

# 6. Remote Desktop Architecture

Do NOT blindly route all traffic through the central server.

Design the system using:

1. Signaling server
2. Direct peer-to-peer connection when possible
3. Relay server as fallback when direct connectivity is impossible

Preferred architecture:

Support Agent
|
| signaling
v
Server
|
| signaling
v
Customer Agent

After connection establishment:

Support Agent <--------> Customer Agent

If direct communication is impossible:

Support Agent <------> Relay Server <------> Customer Agent

The architecture must be designed so that the relay server does not become an unnecessary bottleneck.

# 13. Security

Security is a first-class requirement.

All communication must use encryption.

Use TLS for server communication.

Remote session traffic must be authenticated and encrypted.

Design against:

* Man-in-the-middle attacks
* Session hijacking
* Unauthorized remote access
* Replay attacks
* Token theft
* Brute force
* Path traversal
* Arbitrary file execution
* Privilege escalation
* Unauthorized session creation

Customer must explicitly approve remote access.

The server must verify that a Support Agent is authorized to initiate the requested session.

Every support session must have an auditable identity.

---

# 14. Support Authorization

The server must distinguish between:

SUPPORT_AGENT

CUSTOMER_AGENT

A Customer Agent must never be able to impersonate a Support Agent simply by modifying its local configuration.

Authorization must be enforced server-side.

Do not rely only on hidden UI buttons or client-side restrictions.

---

This is extremely important.

2. Create the architecture.
3. Create a detailed implementation plan.
4. Create the solution and projects.
5. Make sure everything compiles.
6. Implement one subsystem at a time.
7. Run tests after every meaningful phase.
8. Fix compilation errors immediately.

10. Never leave TODO placeholders for core functionality.

Do not give me pseudo-code for core features.

Implement real, buildable code.
